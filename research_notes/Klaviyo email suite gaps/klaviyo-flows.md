# Klaviyo Flows (automations) for Shopify — inventory as of 2026-09-24

Scope: product behavior and API surface for rebuilding Klaviyo flows in another email suite. Primary sources are Klaviyo Help Center and the stable Flows OpenAPI (revision default `2026-07-15`). Agency blogs are used only to separate “what brands build” from “what Klaviyo ships.” Marketing flow messages and transactional flow messages are different statuses on a message, not different flow types.

## Complete list of flow triggers

### Takeaway
A flow has exactly one trigger. Klaviyo’s trigger article (updated 17 Mar 2026) lists six user-facing types: added to list, added to segment, metric, date property (profile or custom object), price drop, and low inventory. Back in stock is not its own trigger type; it is a metric flow (`Subscribed to Back in Stock`) plus a special delay. The API also reports `Unconfigured` for a draft flow whose trigger is not set. Shopify’s canonical metric names differ from the older “Started Checkout” wording still used in flow how-tos.

### Cited Findings
- A flow starts when someone takes a tracked action (metric), is added to a list or segment, has a profile date property, has an item they viewed or started checkout with drop in price, or has a date property on a custom object tied to the profile. Qualification is immediate when the trigger is met. — [Understanding flow triggers and filters](https://help.klaviyo.com/hc/en-us/articles/115002779051)
- The same article enumerates six trigger types: Added to list (welcome series), Added to segment (useful when several actions should qualify someone), Metric (integration events or API events; example abandoned cart on *Started Checkout* plus a profile filter that they have not placed an order), Date property (on, or before, a date; repeats monthly or yearly; fires when the date is added or updated on the profile or a related custom object), Price drop (fixed amount such as $10 or a percent such as 20% on an item viewed or started at checkout), Low inventory (viewed or started checkout; threshold on a variant or the whole product). — [Understanding flow triggers and filters](https://help.klaviyo.com/hc/en-us/articles/115002779051)
- Performance metrics such as *Opened Email* and *Clicked Email* cannot be used to trigger flows. The same page still discusses Apple MPP if someone is “triggering flows off of opens,” which conflicts with that prohibition. — [Understanding flow triggers and filters](https://help.klaviyo.com/hc/en-us/articles/115002779051)
- Getting started (updated 30 Mar 2026) says the builder offers five options — list, segment, metric, price drop, date property — and does not mention low inventory. That is behind both the trigger article and the API. — [Getting started with flows](https://help.klaviyo.com/hc/en-us/articles/115002774932)
- Stable Flows API (`2026-07-15`): a flow has exactly one trigger. Filterable `trigger_type` values are `Metric`, `Added to List`, `Unconfigured`, `Date Based`, `Price Drop`, `Low Inventory`. `Unconfigured` is the value when the flow is draft and the trigger is not set. `Added to Segment` is not in that enum. — [Flows API overview](https://developers.klaviyo.com/en/reference/flows_api_overview); [stable flows OpenAPI](https://raw.githubusercontent.com/klaviyo/openapi/main/openapi/stable/categories/flows.json)
- Once a trigger is set it cannot be changed. A new trigger requires a cloned flow, because filters and dynamic content depend on the original trigger. — [Understanding flow triggers and filters](https://help.klaviyo.com/hc/en-us/articles/115002779051)
- Default re-entry (article updated 17 Dec 2025): segment and list default to no re-entry; metric (examples *Order Placed*, *Viewed Product*, and the article also groups *Price Drop* and *Low Inventory* here), price drop, low inventory, and date property default to allow re-entry. Customers can switch list/segment flows to allow re-entry or time-based re-entry. Date flows repeat when the date updates or on the annual/monthly schedule. Importing profiles onto a list triggers list flows unless the flow is off first. — [How to create a segment- or list-triggered flow](https://help.klaviyo.com/hc/en-us/articles/360003040052)
- Shopify metrics synced by the integration (data reference updated 18 Nov 2025): *Checkout Started*, *Placed Order*, *Ordered Product*, *Fulfilled Order*, *Fulfilled Partial Order*, *Cancelled Order*, *Refunded Order*, *Confirmed Shipment*, *Delivered Shipment*, *Marked Out for Delivery*, *Active on Site*, *Viewed Product*, *Viewed Collection*, *Submitted Search*, *Added to Cart*. *Active on Site* and *Viewed Product* use a Klaviyo gear icon (onsite snippet); the rest are Shopify-branded. Shipment events sync only when Shopify has them for that carrier. *Refunded Order* is full refunds only, not partial refunds. — [Shopify data reference](https://help.klaviyo.com/hc/en-us/articles/115005080447)
- *Checkout Started* fires after the customer enters email on Shopify checkout (one-page or multi-page). It is not Shopify’s own *Abandoned Checkout* metric. Klaviyo abandoned-cart flows use *Checkout Started*; Shopify’s native abandoned-checkout email uses a different metric and must be turned off manually. — [Shopify data reference](https://help.klaviyo.com/hc/en-us/articles/115005080447)
- Flow how-tos updated as late as 29 Mar 2026 and 20 Feb 2026 still say abandoned cart triggers on *Started Checkout*, browse abandonment on *Viewed Product* (skip if *Started Checkout*), and an alternate cart flow on *Added to Cart* (skip if *Placed Order*). For Shopify, *Added to Cart* requires the Track behavioral events setting. — [How to create an abandoned cart flow](https://help.klaviyo.com/hc/en-us/articles/115002779411); [Troubleshooting a metric-triggered flow](https://help.klaviyo.com/hc/en-us/articles/12278373016603)
- *Placed Order* and *Ordered Product* sync seconds apart (one *Placed Order* per order, one *Ordered Product* per unit). A flow triggered on *Placed Order* that excludes people who *Ordered Product* since starting the flow skips everyone. Best practice is to trigger and filter on *Placed Order*. Klaviyo revenue is `(subtotal + shipping) − discounts` and does not subtract cancels/refunds the way Shopify does. — [Shopify data reference](https://help.klaviyo.com/hc/en-us/articles/115005080447)
- Price drop (article updated 12 Feb 2026): Shopify, BigCommerce, WooCommerce, Magento 2, PrestaShop, Salesforce Commerce Cloud, or a custom/API catalog. Sends only for in-stock items. Does not send to anyone who already bought the item, if inventory is 0 or negative, or if the variant is unpublished. Requires *Ordered Product* and at least one of *Viewed Product* or *Started Checkout* with price and product ID. Custom catalogs need a support request to enable the trigger. — [How to create a price drop flow](https://help.klaviyo.com/hc/en-us/articles/4404249033755)
- Low inventory (article updated 31 Jul 2025): Shopify, BigCommerce, Wix, Magento 2, PrestaShop, Salesforce Commerce Cloud, or a custom catalog. Choose product-level or variant-level stock. Set a threshold and an engagement timeframe that excludes people who recently bought the item. Shopify can track the whole product or one variant. Underlying events cited are *Started Checkout* and *Viewed Product*. — [How to create a low inventory flow](https://help.klaviyo.com/hc/en-us/articles/21374913673243)
- Back in stock is a metric flow on the Klaviyo metric *Subscribed to Back in Stock*, not a seventh trigger type. Do not add trigger or profile filters if every restock subscriber should enter. A *Back in stock delay* holds each person until that item is restocked. Minimum inventory and a notification strategy (customers notified per restocked unit, wait between notifications) limit oversell. Platforms: Shopify, BigCommerce, Magento 2, PrestaShop, Shopware, SFCC, and inventory-aware custom/API catalogs. Shopify and BigCommerce can use Klaviyo forms; other platforms use a theme snippet. — [How to build a back in stock flow](https://help.klaviyo.com/hc/en-us/articles/115003872251)
- Date-property flows (article updated 7 Jul 2025): start on the date, or any number of days, weeks, or months before it; “after” is an on-date start plus a time delay. Repeat: Monthly (31st falls on the month’s last day), Yearly, or Should not repeat (full day/month/year, e.g. due date). Examples named: birthday, anniversary, appointment, subscription date, wedding, pregnancy due date, reorder product. One target-date anchor per flow. Splits placed before that anchor are auto-rejoined and cannot be disconnected. The chosen date property cannot be edited later; clone the flow. Klaviyo evaluates profiles daily and whenever the date is added, updated, or deleted, a full day ahead. Accepted formats such as `YYYY-MM-DD` or `MM/DD/YYYY`; text-typed dates do not appear as triggers. — [How to create a date property-triggered flow](https://help.klaviyo.com/hc/en-us/articles/360002732652)
- Custom-object date flows use the same date trigger, pointed at an object property (pet birthday, appointment, warranty). Repeat monthly, yearly, or never. Library birthday/anniversary flows can be retargeted at an object date. — [How to use custom objects in flows](https://help.klaviyo.com/hc/en-us/articles/35146374047515)
- Metric triggers can be any integration event or an event created with the Events API (example: a *Reset Password* event). A profile-property change alone cannot trigger a flow; fire an event or use a segment. — [Understanding flow triggers and filters](https://help.klaviyo.com/hc/en-us/articles/115002779051); [Events API overview](https://developers.klaviyo.com/en/reference/events_api_overview); [Klaviyo Community: profile property update](https://community.klaviyo.com/developer-group-64/regarding-trigger-flow-based-on-profile-property-update-11890)
- Webhook docs list events that can start a flow, including *Started Checkout*, *Placed Order*, *Viewed Product*, *Subscribed to List*, and added to a segment. *Unsubscribed from List* cannot. — [How to add a webhook action to a flow](https://developers.klaviyo.com/en/docs/how_to_add_a_webhook_action_to_a_flow)
- Trigger filters exist only on metric flows, price-drop flows, and custom-object flows. They read the triggering event or object, not profile properties, and for metrics they are checked only at entry (not again at send time). Custom-object trigger filters are rechecked at every step. Profile filters are checked at entry and before every action (email, SMS, profile-property update). Failing a profile filter skips that step but does not remove the person; they are scheduled for the next step and rechecked. Only top-level event properties can be filtered; the *Extra* / *Details* payload cannot, though it can be rendered in a template. String filters are exact matches. — [Understanding flow triggers and filters](https://help.klaviyo.com/hc/en-us/articles/115002779051)
- Shopify *Placed Order* top-level filter fields include `$value`, Items, Collections, Item Count (line items, not quantity, and not de-duplicated), Discount Codes, Total Discounts, Customer Locale, Source Name (POS vs web), Location Name/ID (needs Shopify Markets enabled on the integration), `OptedInToSmsOrderUpdates`. *Ordered Product* adds Name, Variant Name, SKU, ProductID, Quantity (always 1 per event), Tags, variant options, attributes. — [Shopify data reference](https://help.klaviyo.com/hc/en-us/articles/115005080447)
- Shopify customer properties usable in segments and flows: email, name, address, phone, Locale / Locale: Language / Locale: Country, email and SMS marketing consent, Shopify Tags (e.g. Wholesale, VIP). Profiles deleted in Shopify are not deleted in Klaviyo. Tags added to an order after the event are not re-synced. — [Shopify data reference](https://help.klaviyo.com/hc/en-us/articles/115005080447)

### Inferences
- For a Shopify gap analysis, treat the metric catalog as the Nov 2025 data reference (*Checkout Started*, not *Started Checkout*), and treat lingering “Started Checkout” copy as a docs alias until a live account shows the metric name. Both strings appear in Klaviyo’s own 2025–2026 pages.
- Back in stock, price drop, and low inventory are three different mechanisms. Only the last two are first-class trigger types. Rebuilding “back in stock” requires a subscription event, a per-variant wait, and inventory-gated release, not a generic metric trigger.
- `Unconfigured` is an API status for an unfinished draft, not a trigger a merchant selects.
- List and segment flows are first-class in the UI. The public `trigger_type` filter enum omits `Added to Segment`, so segment flows may be stored under another label or omitted from that filter. Do not assume the API string is `Added to Segment`.

### Gaps
- No 2026 page was found that publishes the live metric display name side by side with the legacy *Started Checkout* string. The conflict is unresolved.
- The API `trigger_type` string for segment-triggered flows was not found (enum lists `Added to List` only).
- Whether a profile already inside a metric flow can hold a second concurrent entry under the Dec 2025 “allow re-entry” setting was not confirmed. A 2024 community answer said they cannot re-enter until they exit. — [Klaviyo Community](https://community.klaviyo.com/developer-group-64/event-triggered-flow-is-only-triggering-once-14935)
- SMS subscribe metric name: quiet-hours docs say *Subscribed to Text Messaging Marketing* for the first SMS welcome message. It was not confirmed as a standard Shopify metric versus a Klaviyo channel metric. — [Understanding text message quiet hours in flows](https://help.klaviyo.com/hc/en-us/articles/4408737146651)
- A public crawl of https://www.klaviyo.com/library/flows returned no template list, so trigger defaults on each library tile were not verified one by one.

## Flow actions

### Takeaway
The builder groups actions as messages, data, and logic. Messages are email, SMS, push, and WhatsApp (WhatsApp flow A/B tests are documented as of July 2026). Data actions are profile-property update, list update, internal alert, and webhook (POST JSON only). Logic is time delay (including time of day and weekdays), splits, and a back-in-stock delay. The stable OpenAPI also includes `code`, `countdown-delay`, `target-date`, `ab-test`, `action-output-split`, and `trigger-branch` action types. Each action is draft, manual, or live, independent of the flow.

### Cited Findings
- Message actions send and have their own live / manual / draft status. Data actions update data (profile property or a list) or do something else data-related (internal alert, webhook). Logic actions are time delays and multi-branch splits (up to 20 paths) that can use profile data and, in metric flows, the triggering event. A time delay only works if a live or manual action follows it. Back-to-back actions with no delay run at the same time. — [Getting started with flows](https://help.klaviyo.com/hc/en-us/articles/115002774932)
- Statuses: Draft (default; nobody is scheduled; a live message flipped to draft is skipped). Manual (scheduled into Needs Review; the person still moves to the next step, so later live messages can send while this one waits). Live (sends automatically). Flipping manual to live does not send the Needs Review queue. Bulk update can set every action, immediately or on a schedule. If every action is draft, nobody enters. — [Getting started with flows](https://help.klaviyo.com/hc/en-us/articles/115002774932); [How to bulk update or schedule flow statuses](https://help.klaviyo.com/hc/en-us/articles/360048376172)
- Time delay units: any number of minutes, hours, or days. “X days” is X × 24 hours unless a time of day is set, in which case days are calendar days. Delays can wait until a time of day or only certain weekdays. Changing a delay does not move messages already scheduled. — [Getting started with flows](https://help.klaviyo.com/hc/en-us/articles/115002774932)
- API time-delay payload example: `unit` (hours), `value`, `secondary_value`, `timezone` (`profile`), `delay_until_time`, `delay_until_weekdays` (e.g. monday–wednesday). — [Flows API overview](https://developers.klaviyo.com/en/reference/flows_api_overview)
- Date flows use a target-date anchor (“wait until the person’s date”) that is distinct from a normal delay. Countdown units in the API are days, weeks, or months. Splits before the anchor rejoin automatically. — [How to create a date property-triggered flow](https://help.klaviyo.com/hc/en-us/articles/360002732652); [stable flows OpenAPI](https://raw.githubusercontent.com/klaviyo/openapi/main/openapi/stable/categories/flows.json) (`CountdownDelayAction`, `TargetDateAction`)
- Back-in-stock delay is unique to back-in-stock flows and is its own API action type `back-in-stock-delay`. — [How to build a back in stock flow](https://help.klaviyo.com/hc/en-us/articles/115003872251); [stable flows OpenAPI](https://raw.githubusercontent.com/klaviyo/openapi/main/openapi/stable/categories/flows.json)
- Profile property update: update an existing property, create one, or delete one; multiple steps in one action, executed in order; list-type properties need one step per value; Klaviyo type-checks the value. If several update actions sit next to each other, put at least a one-minute delay between them. — [How to add an update profile property action to a flow](https://help.klaviyo.com/hc/en-us/articles/360001768432)
- List update (add or remove the profile from a list at a point in the flow) is a documented builder action. — [Build and use flows](https://help.klaviyo.com/hc/en-us/sections/14543521377819)
- Internal alert (formerly “notification”) emails an address when someone reaches a step (detractor NPS, VIP/wholesale list). The recipient does not need a Klaviyo profile or an account seat. — [Build and use flows](https://help.klaviyo.com/hc/en-us/sections/14543521377819)
- Webhooks exist only in flows, fire on flow-triggerable events, and send one POST with a JSON body. Headers are partially hashed in the UI. List/segment/date flows can pass profile properties; metric and price-drop flows can also pass the triggering event. Later customer actions cannot be included. Not GET/DELETE/other verbs. — [Understanding webhooks in flows](https://help.klaviyo.com/hc/en-us/articles/4534329515931); [How to add a webhook action to a flow](https://developers.klaviyo.com/en/docs/how_to_add_a_webhook_action_to_a_flow)
- Push notifications can be added to a flow for an iOS or Android app. — [Build and use flows](https://help.klaviyo.com/hc/en-us/sections/14543521377819)
- WhatsApp is a flow channel: a July 2026 help article covers A/B testing a WhatsApp flow message (open rate or click rate, fixed or dynamic allocation, end on 95% significance, a date, or manually). — [How to do A/B Testing in WhatsApp Flow](https://help.klaviyo.com/hc/en-us/articles/53294750535323)
- Stable OpenAPI action union (revision `2026-07-15`) includes, among others: `SendSmsAction`, `SendWebhookAction`, `SendInternalAlertAction`, `SendWhatsAppAction`, `SendWhatsAppWithACAction`, `TimeDelayAction`, `TriggerBranchAction`, `UpdateProfileAction`, `TargetDateAction`, `CountdownDelayAction`, `AbTestAction`, `CodeAction` (type `code`), `InternalServiceAction` (type `internal-service`; data variants are scheduled report, track event, report builder, or unknown — this reads as a Klaviyo-internal action, not a merchant step), `action-output-split`, `back-in-stock-delay`, `conditional-split`, and `SendPushNotificationAction` (referenced as a main action inside experiments). Flow message channel objects include email, push, SMS, webhook, and WhatsApp. — [stable flows OpenAPI](https://raw.githubusercontent.com/klaviyo/openapi/main/openapi/stable/categories/flows.json)
- Email send-action fields in the definition include from email/label, reply-to, cc, bcc, subject, preview text, template id, `smart_sending_enabled`, `transactional`, tracking params, `additional_filters`, and status. SMS fields include body, smart sending, `transactional`, tracking, `respecting_sms_quiet_hours`, and additional filters. — [Flows API overview](https://developers.klaviyo.com/en/reference/flows_api_overview)
- Legacy flow-action resource still exposes `action_type` such as `SEND_EMAIL`, `send_options.use_smart_sending`, `send_options.is_transactional`, open/click tracking, and UTM options. — [Flows API overview](https://developers.klaviyo.com/en/reference/flows_api_overview)
- Splits evaluate once, when the profile reaches them. A delay belongs before the split if the branch depends on something that might happen during the wait (placed an order); trigger-event fields (cart value) are known immediately and do not need a pre-split delay. Paths can be rejoined. — [Understanding time delays near splits](https://help.klaviyo.com/hc/en-us/articles/360050334651)
- Legacy trigger split (article updated 12 Aug 2025) is YES/NO on trigger dimensions, and only on metric and price-drop flows (example: cart value). The June 2026 multi-branch article says the new split replaces both the conditional split and the trigger split; existing flows keep the old components. — [How to add a trigger split to a flow](https://help.klaviyo.com/hc/en-us/articles/115003885632); [Multi-Branch Splits](https://help.klaviyo.com/hc/en-us/articles/52369094030235)

### Inferences
- A parity builder needs at least: email, SMS, push, WhatsApp, webhook POST, profile-property write/delete, list add/remove, internal alert, time delay with timezone + clock time + weekdays, conditional/trigger/multi-branch splits, back-in-stock delay, and date-flow countdown/target-date delays.
- `code` and `action-output-split` are in the public schema, so a strict rebuild should not assume the canvas is only the classic help-center blocks. Product copy for those two was not retrieved.
- `SendWhatsAppWithAC` is a second WhatsApp action. What “AC” means was not documented in the pages read.
- `internal-service` should not be exposed as a customer action; it looks like Klaviyo’s own scheduled jobs stored in the same graph.

- List-update help article body was not fetched; only the help-center index title and summary. Exact options (which lists, subscribe vs member) are unconfirmed.
- Push action settings (rich media, deep links, quiet hours) were not fetched beyond “you can add a push to a flow” and Smart Sending’s 24-hour push window.

## What conditional-split condition types exist

### Takeaway
As of 29 Jun 2026, new splits are multi-branch: up to 19 ordered conditions plus a permanent Everyone else path, first match wins. Conditions use the same filter builder as segments: events, profile properties, location, list or segment membership, email/SMS marketing consent, predictive analytics, random sample, and (metric flows only) trigger-event properties, combined with AND/OR. An older conditional-split article also lists EU (GDPR) and proximity to a location. Random sample is a split condition, not the per-message A/B test.

### Cited Findings
- Multi-branch split (updated 29 Jun 2026): up to 20 paths (19 defined + Everyone else, always last, not removable). Profiles are checked in path order and take the first match; they cannot take two paths. A path with no conditions is false and skipped. If every configured path is empty, everyone goes to Everyone else. Existing flows are unchanged; multi-branch applies to new splits. It replaces chained conditional splits and trigger splits. — [Multi-Branch Splits](https://help.klaviyo.com/hc/en-us/articles/52369094030235)
- Path conditions: what someone has or hasn’t done; properties about someone; location; list or segment membership; whether they can or can’t receive email or SMS marketing; predictive analytics (examples: predicted CLV, churn risk); random sample (a percentage of profiles evaluated for that path); trigger-event properties such as order value (metric-triggered flows only). AND/OR. You can preview a profile’s path before going live. — [Multi-Branch Splits](https://help.klaviyo.com/hc/en-us/articles/52369094030235)
- Older conditional-split article (YES/NO) lists: what someone has done or not done; properties about someone; whether someone is in the EU (GDPR); proximity to a location; in or not in a list; can or cannot receive marketing; predictive analytics; random sample. YES meets the condition. A delay must sit before the split if the condition is “did they do X within a window.” — [How to add a conditional split to a flow](https://help.klaviyo.com/hc/en-us/articles/115003872171)
- Branching best practices (updated 6 Jul 2025, and the copy already uses Everyone else): purchasers vs not (`Has Placed Order at least once over all time`); country equals US vs everyone else; several regions as ordered paths (US, then Canada, then UK, else everyone); product category/collection on metric flows, most specific path first. — [Understanding branching best practices for flows](https://help.klaviyo.com/hc/en-us/articles/360051182592)
- Custom objects in splits: triggering object’s properties (metric/date object flows), or “properties about someone” across all of that profile’s objects (count of records, existence/status, up to 5 additional where-clauses in the object example). — [How to use custom objects in flows](https://help.klaviyo.com/hc/en-us/articles/35146374047515)
- API conditional split example uses `profile-marketing-consent` with `channel: sms`, `can_receive_marketing: true`, and `consent_status.subscription: subscribed`. A community paste of a flow definition also shows `profile-not-in-flow` and `profile-property` condition types. — [Flows API overview](https://developers.klaviyo.com/en/reference/flows_api_overview); [Klaviyo Community, Dec 2025](https://community.klaviyo.com/service-35/flow-trigger-filter-profile-not-in-flow-gives-error-when-trying-to-adjust-it-18670)
- Marketing site (less precise than help) says conditional splits can use actions taken, subscriber data, location, list membership, predictive analytics, and random sample, and that trigger splits use data about the event that started the flow and are not available on every flow. — [Klaviyo Flows feature page](https://www.klaviyo.com/features/flows)

### Inferences
- Consent is a first-class split dimension (can/cannot receive email or SMS marketing), separate from “is on list X.” A rebuild that only checks list membership will not match Klaviyo.
- Random sample on a path is how Klaviyo A/B-tests whole branches (timing, extra messages, discounts). It is not a statistical winner engine.
- The June 2026 article does not repeat “in the EU” or “proximity.” Those may still be inside “location,” or they may only remain on old YES/NO splits. Do not drop them from a gap list until a live builder confirms they are gone.

### Gaps
- Full operator list (equals, contains, at least, in the last N days, etc.) was not copied from the segment-builder reference. The trigger article only confirms exact match for equals / doesn’t equal / contains / doesn’t contain, and that values can be pasted if they are not yet in the dropdown.
- Segment membership is named in the June 2026 multi-branch article. A 20 Sep 2026 community thread says segment conditions do not show up in profile filters and suggests writing a profile property from a segment-triggered flow instead. Those two sources conflict; it is unclear whether the gap is profile filters only, a UI bug, or a plan limit. — [Klaviyo Community](https://community.klaviyo.com/marketing-30/why-can-t-we-use-segments-as-a-profile-trigger-in-a-flow-19752)
- Predictive field list inside the split picker (which of CLV, churn, gender, next-order date, predicted order count) was not enumerated beyond “predicted CLV or churn risk” plus Academy examples.
- `action-output-split` condition shape was not read out of the schema.

## How A/B tests in flows work

### Takeaway
There are two different mechanisms. A message-level test varies content of one email (and, separately, a WhatsApp message) and can auto-pick a winner on open rate or click rate. A branch test uses a random-sample split to vary timing, number of messages, or offers, and a human picks the winner from analytics. Flow-email auto-winner metrics are only open rate and click rate, not revenue. No first-class holdout group was documented. A 2024 API guide said A/B actions could not be created via API; the 2026 OpenAPI schema includes `AbTestAction`, so that limit may be stale.

### Cited Findings
- Flow email A/B test (article updated 18 Aug 2025): one flow email, two or more variations. You can change subject, preview text, sender name, sender email, and body (including plain text vs HTML, or a discount). At least two variations; more are clones. Variations can be deleted only while the test is draft, and never below two. Each variation has a weight (equal weights recommended). “Automatically choose distribution” starts even, then shifts traffic toward the better variation while the test is still running. — [How to A/B test a flow email](https://help.klaviyo.com/hc/en-us/articles/6960371049115)
- Winner selection defaults to click rate. The only other winning metric for flow emails is open rate. Click rate is recommended because Apple MPP inflates opens. Automatic end options: statistical significance (on by default), a date limit, or both (whichever first). You can turn automatic selection off and choose a winner manually. Choosing a winner makes that variation the message for everyone afterward. Moving the message from live to draft ends the test and auto-selects by the winning metric; a tie keeps the first variation. Publishing a test on an email that was already live stops analytics on the original and tracks the copies separately. Results shown: recipients, opens, clicks, and the email’s conversion metric (for example *Placed Order*) — conversion is reported, not offered as the auto-winner metric. — [How to A/B test a flow email](https://help.klaviyo.com/hc/en-us/articles/6960371049115)
- Branch tests (updated 22 Feb 2026): a split with a random-sample condition and a percentage (often 50). Use the other path for a different delay, an extra email, or a discount. Test one major variable. Compare open, click, conversion, and revenue in flow analytics, then change the split so later people only take the winning path. There is no automatic statistical winner for branch tests. — [How to A/B test flow branches](https://help.klaviyo.com/hc/en-us/articles/360049849432); [Understanding what to A/B test in your flows](https://help.klaviyo.com/hc/en-us/articles/360054629031)
- WhatsApp flow A/B (updated 19 Jul 2026): winning metric is open rate or click rate; allocation is a fixed percentage or dynamic; end on statistical significance described as 95% probability, a date, or manually. Winner becomes the default template. UTM can be tracked per variation. — [How to do A/B Testing in WhatsApp Flow](https://help.klaviyo.com/hc/en-us/articles/53294750535323)
- OpenAPI `AbTestAction` includes `current_experiment` fields: allocations, variations, `automatic_winner_selection_settings` (`automatic_end_date`, `automatic_end_statistical_certainty`, `enabled`). Push and WhatsApp actions are valid `main_action` / variation types in that experiment object. — [stable flows OpenAPI](https://raw.githubusercontent.com/klaviyo/openapi/main/openapi/stable/categories/flows.json)
- The 15 Oct 2024 beta guide said create-flow did not support A/B test actions for email and SMS, and that a flow could not be updated after create. That page is explicitly an old revision. — [Create flows (v2024-10-15)](https://developers.klaviyo.com/en/v2024-10-15/reference/create_and_retrieve_flows)
- No Klaviyo help page retrieved describes a holdout group inside a flow A/B test. The closest control is a random-sample path that you leave on the old experience, or an unequal variation weight.

### Inferences
- Rebuilding “Klaviyo A/B” means two features: (1) a per-message experiment with sticky winner and only open/click as the decision metric, and (2) a manual branch experiment that can change the graph, not just the creative.
- Dynamic allocation while the test runs is not the same as ending the test. People can still see the losing variation until a winner is chosen.
- Revenue can be read on the results page but will not auto-promote a winner. A suite that picks winners on placed-order rate is stricter than Klaviyo’s flow-email test and closer to what operators actually want.

### Gaps
- SMS message-level A/B (as opposed to WhatsApp and email) was not confirmed in a 2025–2026 help article. The 2024 API note mentioned email and SMS variants; the 2026 WhatsApp article is a separate product surface.
- The minimum sample size, the exact significance test, and whether dynamic allocation uses a bandit were not specified beyond “high statistical certainty” (WhatsApp page says 95%).
- Whether create-flow in revision `2026-07-15` accepts `AbTestAction` was not proven by a successful example. The schema includes it; the last explicit limitation is the 2024 beta guide.
- Holdout as a named flow feature: not found. A third-party 2026 article claims Smart Sending can cancel an A/B test that gets no results; that claim was not checked against a Klaviyo page and is not treated as fact. — [Everboost](https://everboost.co.uk/insights/klaviyo-smart-sending/)
- Subject-line-only vs full-template variation limits, and whether a test can vary the delay on a single message without a branch split, were not documented. Timing tests are described only as branch tests.

## Smart sending, quiet hours, transactional vs marketing, filters, re-entry

### Takeaway
Smart Sending skips a marketing message and does not reschedule it. Defaults are 16 hours for email and 24 hours for SMS and push, per channel, per message. SMS quiet hours delay instead of skip, and are checked before Smart Sending. Transactional is a per-message flag on paid accounts, mostly for metric-triggered flows, and it bypasses Smart Sending and (by default) SMS quiet hours. It is not a property of the whole flow. Profile filters and per-message additional filters can skip one step without ending the flow. Re-entry is now a trigger setting: once, whenever they qualify again, or after a minimum wait.

### Cited Findings
- Smart Sending windows (help article, also mirrored in 2026 translations): email 16 hours, SMS 24 hours, push 24 hours. Windows are independent. Changing the window is not retroactive; people already inside the old window stay in it. Skipped messages are not rescheduled. SMS/push skips can be resent manually. Smart Sending applies only to marketing messages. Transactional messages are always sent and receiving one does not start a Smart Sending window, on every channel. Campaigns default on. On a flow message the control is “skip recently emailed / texted profiles.” Many pre-built flows ship with it on; it can be turned off per message. Email settings include an “ignore transactional messages” checkbox. — [Understanding Smart Sending in Klaviyo](https://help.klaviyo.com/hc/en-us/articles/115002779311)
- For repeated triggers (*Viewed Product*, *Active on Site*), Klaviyo recommends leaving Smart Sending on. Alternative frequency caps: an additional filter on *Received email* with that subject zero times in the last X days, or a profile filter “has not been in this flow in the last X days.” — [Troubleshooting why a profile is scheduled in a flow multiple times](https://help.klaviyo.com/hc/en-us/articles/115002779491)
- SMS quiet hours (updated 9 Sep 2026) are evaluated at send time, follow daylight saving, and are checked before Smart Sending. Default calculation uses area codes for US/Canada and the country’s eastern time zone internationally; an alternate mode applies that eastern zone to everyone in the country. If quiet hours block a send, Klaviyo delays until they end, then applies Smart Sending: send if the window has passed, otherwise skip. Quiet hours can be toggled per flow SMS. They are off by default on transactional SMS, but can be turned on. They do not apply to Klaviyo’s default keyword replies (Yes, Stop, Help); they do apply to custom subscribe-keyword messages. France: quiet hours do not apply to transactional SMS or to the first message of an SMS welcome flow triggered by *Subscribed to Text Messaging Marketing*. — [Understanding text message quiet hours in flows](https://help.klaviyo.com/hc/en-us/articles/4408737146651)
- Transactional email (help article): not marketing, so people expect them and suppressed profiles still receive them, with some suppression reasons excluded (the article’s exception list was not fully captured). Paid accounts only. Metric-triggered flows only, such as *Placed Order*. Cannot be used in price-drop flows. Applied per email, not per flow: one email in a series can be transactional and the rest marketing. You cannot flip an entire flow to transactional, but every email in a flow can be approved individually. Approval can take up to 24 hours. Editing the message removes transactional status and requires resubmission. Cannot be imported from the ecommerce platform. Apply from the message sidebar. — [How to use flows to send transactional emails](https://help.klaviyo.com/hc/en-us/articles/360003165732)
- Klaviyo’s own best-practices page (14 Sep 2026) repeats that order confirmation, shipping confirmation, and delivery updates can be sent from Klaviyo, that unsubscribed people do not get marketing but do get transactional mail, and that you request status per message and hear back within 24 hours. — [Email marketing best practices](https://www.klaviyo.com/products/email-marketing/best-practices)
- API: `transactional: false` and `smart_sending_enabled: true` are separate booleans on flow email and SMS. SMS also has `respecting_sms_quiet_hours`. — [Flows API overview](https://developers.klaviyo.com/en/reference/flows_api_overview)
- Additional filters sit on one email or SMS, use the same condition builder as profile filters, and only affect that message. A skip does not exit the flow. Example: send message 5 only to people who have not purchased since the flow started, or who have not opened a specific subject. — [Understanding flow triggers and filters](https://help.klaviyo.com/hc/en-us/articles/115002779051)
- Profile filters are rechecked before each action. Trigger filters (metric) are not. Someone who fails at send time is skipped and still moves forward. Abandoned cart’s canonical profile filter is “placed order zero times since starting this flow.” — [Understanding flow triggers and filters](https://help.klaviyo.com/hc/en-us/articles/115002779051); [Getting started with flows](https://help.klaviyo.com/hc/en-us/articles/115002774932)
- Re-entry lives on the trigger, not only as a “has not been in this flow” filter. Options: enter only once; re-enter whenever they qualify again; re-enter after a minimum time. Re-entry is checked only when they enter organically, not at every step. Defaults: list and segment no re-entry; metric, price drop, low inventory, and date property allow re-entry. — [Understanding flow triggers and filters](https://help.klaviyo.com/hc/en-us/articles/115002779051); [How to create a segment- or list-triggered flow](https://help.klaviyo.com/hc/en-us/articles/360003040052)
- Welcome series should be separate email and SMS flows, because opt-in is per channel and each welcome flow is entered once. — [Getting started with flows](https://help.klaviyo.com/hc/en-us/articles/115002774932)
- Past profiles can be pulled into a flow after it goes live or manual (back-population). That is a builder operation, not an API enroll-by-id call. — [Getting started with flows](https://help.klaviyo.com/hc/en-us/articles/115002774932) linking to [How to add past profiles to a flow](https://help.klaviyo.com/hc/en-us/articles/360049924272)
- Flow message settings also include UTM tracking (on/off, or company defaults). — [Getting started with flows](https://help.klaviyo.com/hc/en-us/articles/115002774932); [Flows API overview](https://developers.klaviyo.com/en/reference/flows_api_overview)

### Inferences
- A clone that treats “transactional flow” as a flow type will be wrong. Model a boolean on each message, plus an approval state, plus “this send ignores marketing suppression and Smart Sending.”
- Quiet hours and Smart Sending compose in a fixed order for SMS: delay for quiet hours, then skip-or-send for Smart Sending. Email has no equivalent quiet-hours delay in the sources read.
- High-intent flows (abandoned checkout) are the ones operators turn Smart Sending off for, because a skip is permanent. Prebuilt flows often leave it on, so a migration should preserve the per-message flag rather than a global default.

### Gaps
- The exact suppression reasons that still block transactional email were not copied (the article says suppressed people receive them, then notes exceptions).
- Transactional SMS approval rules versus email were not fully compared. Quiet hours say transactional SMS exist and default quiet hours off; the email article’s “metric-triggered only / not price drop / paid / 24h review” was not confirmed word for word for SMS.
- Email quiet hours or a send-time blackout for marketing email were not found.
- Smart Send Time / Personalized Send Time is a campaign/analytics feature in secondary 2026 writeups, not documented here as a flow-message control. Not treated as a flow action.
- Numeric limits on additional filters (how many conditions) were not stated.
- Back-population eligibility rules (which trigger types, whether it sends immediately) were not read; only that the feature exists.

## What Klaviyo cannot do via API

### Takeaway
You cannot place a profile into a flow by flow id. The stable API can create a flow from a definition, read the definition, list and update actions, and set flow status (draft / manual / live). Enrollment is indirect: create an event, add someone to a list (or qualify a segment), or set a date property, and let the trigger fire. Create-flow rate limits are tight (100/day). A 2024 beta page said the definition could not be updated after create and A/B actions could not be created; 2026 has per-action update and an `AbTestAction` schema, but a full-graph update endpoint is still not described in the overview.

### Cited Findings
- Flows API categories: create and fetch flows, update flow status, relationship endpoints for actions and tags. Use cases explicitly include get actions, set status to live / manual / draft, read email and SMS messages, get the email template, create a metric-triggered abandonment flow, create a date-triggered birthday flow, create a price-drop flow, and read a definition via `additional-fields[flow]=definition`. — [Flows API overview](https://developers.klaviyo.com/en/reference/flows_api_overview)
- `POST /api/flows` creates a flow from an encoded definition. New actions use `temporary_id` (replaced by real ids). Rate limits: burst `1/s`, steady `15/m`, daily `100/d`. Scope `flows:write`. Flows are created in Draft unless the request sets action status. Klaviyo says it does not recommend pre-creating flows in customer accounts. Recommended path: build in the UI, GET the definition, strip `relationships`, `links`, `created`, `updated`, `status`, and `trigger_type`, swap action `id` for `temporary_id`, then POST. — [Flows API overview](https://developers.klaviyo.com/en/reference/flows_api_overview); [Create Flow](https://developers.klaviyo.com/en/reference/create_flow)
- Exactly one trigger per flow. Definition includes `profile_filter`, `entry_action_id`, `triggers`, `actions`. — [Flows API overview](https://developers.klaviyo.com/en/reference/flows_api_overview)
- Get flows supports `filter` (including `trigger_type`), `sort`, sparse `fields`, and `include`. Get flows triggered by a metric: `GET /api/metrics/{metric_id}/flow-triggers` (documented for metrics created by your OAuth app; the example uses a Shopify *Placed Order* id). — [Flows API overview](https://developers.klaviyo.com/en/reference/flows_api_overview)
- Update Flow Action is `PATCH /api/flow-actions/{id}`, scope `flows:write`, burst `3/s`, steady `60/m`, revision default `2026-07-15`. A March 2026 community thread from a production integration (Grid & Pixel) shows create-flow and flow-action update in real customer accounts (a server 500 was fixed the next day). — [Update Flow Action](https://developers.klaviyo.com/en/reference/update_flow_action); [Klaviyo Community, Mar 2026](https://community.klaviyo.com/developer-group-64/breaking-api-change-on-flows-create-and-flow-action-update-api-endpoints-19084)
- Ruby SDK notes: `delete_flow`, `delete_flow_action`, and `update_flow` described as updating the status of a flow and all of its actions (burst `3/s`, steady `60/m`, `flows:write`), not as replacing the definition. — [klaviyo-api-ruby changelog](https://github.com/klaviyo/klaviyo-api-ruby/blob/main/CHANGELOG.md); [RubyDoc FlowsApi](https://rubydoc.info/gems/klaviyo-api-sdk/14.0.0/KlaviyoAPI/FlowsApi)
- v2024-10-15 beta limitations, not repeated in the current overview: no A/B variant creation for email and SMS; no way to update a flow after create (“planned”). The current overview’s create section still walks through creating a new flow from a copied definition rather than PATCHing the graph. — [Create flows (v2024-10-15)](https://developers.klaviyo.com/en/v2024-10-15/reference/create_and_retrieve_flows); [Flows API overview](https://developers.klaviyo.com/en/reference/flows_api_overview)
- Drag-and-drop templates on API-created flows: create HTML or hybrid templates via the Templates API. App partners are limited to two drag-and-drop templates, issued as `template_id`s by Klaviyo after a form submission, then cloned per account. — [Flows API overview](https://developers.klaviyo.com/en/reference/flows_api_overview)
- No Flows endpoint in the overview enrolls a profile by flow id. Documented ways to cause entry: Events API custom events “that can be used to trigger flows”; adding/subscribing a profile to a list for a list trigger; a segment the profile newly qualifies for; a date property; price drop and low inventory, which are catalog-driven. A 2022 support reply said there was no API to start an arbitrary flow for a profile and that the profile must hit the trigger (list subscribe vs mere list member was a meaningful difference). That quote is old; the 2026 overview still has no enroll endpoint, which is the current evidence. — [Flows API overview](https://developers.klaviyo.com/en/reference/flows_api_overview); [Events API overview](https://developers.klaviyo.com/en/reference/events_api_overview); [Klaviyo Community, 2022](https://community.klaviyo.com/developer-group-64/adding-a-user-to-a-list-by-api-v2-is-not-triggering-the-flow-how-do-i-do-this-3355)
- You also cannot retarget an existing flow via API in any documented way: the UI itself forbids trigger changes and requires a clone. — [Understanding flow triggers and filters](https://help.klaviyo.com/hc/en-us/articles/115002779051)
- Opens and clicks cannot be the metric you select as a flow trigger, so posting an *Opened Email* event is not a supported way to enroll someone. — [Understanding flow triggers and filters](https://help.klaviyo.com/hc/en-us/articles/115002779051)
- In-app JSON view: open the flow, replace `/edit` with `.json`. Useful for copying a definition, not for enrollment. — [Flows API overview](https://developers.klaviyo.com/en/reference/flows_api_overview)

### Inferences
- A migration tool can clone flow structure (within the action types the create schema accepts) and can turn flows on, but it cannot “seed” historical profiles through the API except by backdating events, list subscriptions, or date properties — and those will also affect segments, attribution, and other flows.
- Daily create cap of 100 flows per account matters if a partner app stamps a full Shopify lifecycle into many accounts.
- Assume status updates and single-action updates work in 2026. Do not assume a PUT of the whole definition works. Do not assume A/B tests round-trip until a create call with `AbTestAction` is shown to succeed; the schema and the last written limitation disagree.
- List “member” vs “subscribe” still matters for welcome flows. Copying profiles onto a list without a subscribe may not match a consent-gated welcome.

### Gaps
- Whether revision `2026-07-15` create accepts every schema action (`code`, `ab-test`, `send-whatsapp`, `action-output-split`, `list update`) was not tested. The overview’s narrative examples are time delay, conditional split, SMS, and email.
- A dedicated 2026 sentence of the form “there is no enroll-by-flow-id endpoint” was not found. The conclusion is from the absence of that route on the current Flows API surface, plus the 2022 support reply.
- Rate limits for Get Flow and Get Flows were not copied (action reads are `3/s` and `60/m` in the SDK comments). Create is the only limit quoted from the current docs page: `1/s`, `15/m`, `100/d`.
- Webhook action create/update via API (URL, headers, secret rotation) was not verified beyond the action being in the schema.
- OAuth scope differences vs private-key `flows:read` / `flows:write`, and whether metric flow-trigger listing works for Shopify’s metric rather than only “metrics created by your OAuth app,” are unclear. The overview both restricts that route to the app’s metrics and shows a Shopify Placed Order example.

## Predictive analytics used inside flows

### Takeaway
Klaviyo still documents predicted CLV, churn risk, expected date of next order, average time between orders, predicted order count, and predicted gender. Gender was not found to be removed as of the latest help and Academy pages (through 2026). In flows, these show up as split/segment conditions (“predictive analytics about someone”) and, for expected next order date, as a date-property trigger. They are not a separate flow-trigger type. The model needs purchase history; a new store will not have them.

### Cited Findings
- Help center (updated 4 Aug 2025): predictive analytics on the profile’s Metrics and Insights tab include Historic CLV, Predicted CLV, Total CLV, Churn Risk Prediction, and Average Time Between Orders. CLV is modeled from the account’s data and updated weekly. Expected date of next order uses that customer’s behavior and the store’s overall pattern. Predictions are averages and are meant for groups. — [Understanding Klaviyo's predictive analytics](https://help.klaviyo.com/hc/en-us/articles/360020919731)
- The same article still documents predicted gender: first name plus census data → likely male, likely female, or uncertain, and tells marketers not to rely on it exclusively. — [Understanding Klaviyo's predictive analytics](https://help.klaviyo.com/hc/en-us/articles/360020919731)
- Academy (lesson recorded in the predictive-analytics course materials, page fetched 2026): metrics that appear once the account qualifies are Historic CLV, Predicted CLV, Total CLV, Churn risk prediction, Average time between orders, Predicted gender, and Expected date of next order. Default CLV window is 365 days. Custom CLV (change the window) requires Klaviyo CDP. Account thresholds listed for the model: at least 500 customers who ordered, 180 days of order history, at least one order in the last 30 days, and some customers with 3+ orders. A date flow can start on *Expected date of next order* a chosen time before that date (example: 2 days before). — [Klaviyo Academy: custom CLV](https://academy.klaviyo.com/en-us/courses/getting-started-with-marketing-analytics/lessons/custom-clv)
- Helpdesk panel (updated 26 Jan 2026): CLV, total orders, churn risk, predicted next order date. Churn risk is the predicted probability of no purchase in the next 90 days: Low under 33%, Medium 33–66%, High over 66%. Predicted next order date needs at least two historical orders. New stores can show “not enough data yet.” The panel is read-only. — [Klaviyo Helpdesk Predictive Insights Panel](https://help.klaviyo.com/hc/en-us/articles/40813462564763)
- Product page (11 Aug 2026): predicted CLV, expected next order date, and churn risk are calculated on profiles and can drive auto-updating segments. It does not say gender was removed. — [Predictive analytics for ecommerce](https://www.klaviyo.com/solutions/ai/predictive-analytics-for-ecommerce)

### Inferences
- Predicted gender is still offered as of the August 2025 help article and Academy materials current in 2026. Nothing retrieved says it was sunset. A rebuild can include it, but it is an inference from a first name, not a Shopify field.
- Churn risk has two layers in the sources: a numeric prediction on the profile, and a helpdesk bucket (low/medium/high over a 90-day no-purchase probability). Flow splits may expose the raw property; the helpdesk buckets may be UI-only. Not confirmed.
- Expected next order date is the only predictive field documented as a flow trigger (because it is a date). CLV, churn, gender, and order count are branch or filter conditions, or segment definitions that can then trigger a segment flow.
- These fields will be empty on a new Shopify store. Any cloned replenishment flow should no-op until the model populates.

### Gaps
- The exact property keys shown in the flow builder (`Predicted CLV` vs `$predicted_clv`, churn as a probability vs a label) were not captured from a definition JSON.
- Whether predicted gender still appears in the split builder in September 2026, or only on the profile and in older Academy copy, was not confirmed in the June 2026 splits article (that article names CLV and churn only).
- Custom CLV’s effect on flow splits (does the split use the custom window?) was not stated.
- No source confirmed predictive analytics as an API field you can set. They are computed. A migration cannot copy Klaviyo’s scores unless a profiles/read endpoint returns them; that read API was out of scope and not checked.
